# 07 · 宿主适配

## 1. 两条控制路径

| 路径 | 内容 | 依赖 | 失效后果 |
|---|---|---|---|
| 主路径 | 温暖度 W、字数上限、问句上限，以提示词形式写入 | 所有模型 | 执行打折扣 |
| 副路径 | `temperature`、`top_p` | 视模型而定 | 不支持的模型忽略，主路径照常 |

模型专有参数不出现在 `SKILL.md` 正文中。需要改动时只改本文件与 `config.json`。

## 2. 宿主参数

| 宿主 | 温度支持 | 建议值 | 控制方式 |
|---|---|---|---|
| `deepseek-chat`（非思考） | 支持 | 0.6-0.8 | 温度 + 提示词 |
| `deepseek-reasoner` 或思考模式 | 不支持，设置后不生效 | 不设置 | 仅提示词 |
| `gemini-3-pro` / `gemini-3-flash` | 支持 | 保持默认 1.0 | 温度 + 提示词 |
| `qwen-max` / `qwen-plus`（非思考） | 支持 | 0.6-0.8 | 温度 + 提示词 |
| `qwen3`（思考） | 支持 | 0.6 左右 | 温度 + 提示词 |
| `claude-*` | 支持 | 0.6-0.8 | 温度 + 提示词 |

DeepSeek 思考模式不支持 `temperature`、`presence_penalty`、`frequency_penalty`，设置这些参数不会报错，也不会生效。此类模型只使用提示词路径。

支持温度的模型按 W 微调：

```
T = 0.7 + 0.05 × (W − 3)
W1 → 0.60   W2 → 0.65   W3 → 0.70   W4 → 0.75   W5 → 0.80
```

调整范围控制在 ±0.1 以内。温度只影响措辞随机性，不影响共情程度。

危机场景不调整温度，保持该模型默认值。

## 3. 思考预算与截断

推理模型的思考与回答共享同一个输出预算。思考越长，留给回答的余量越少，常见表现是回复断在半句，或者末尾的状态向量整段丢失。轮次切换快、上下文接近上限时更容易出现。

### 3.1 宿主侧设置

| 宿主 | 参数 | 常规轮次 | 复杂轮次 |
|---|---|---|---|
| DeepSeek 思考模式 | `reasoning_effort` | `low` 或 `medium` | `high` |
| Gemini 3 | thinking budget | 尽量小，能关则关 | 放开 |
| Qwen3 | `enable_thinking` | 关闭 | 开启 |
| 通用 | `max_tokens` | 不低于 1024，推荐 2048 | 2048 到 4096 |

判断依据是任务复杂度，不是重要性。日常情绪对话属于简单任务，长时间思考不会提升质量，只会挤掉回答。

### 3.2 技能侧压缩

`SKILL.md` 第 0 节给出三档思考模式。默认用紧凑模式：只在脑内维护 24 个整数，不写评估理由，不复述用户原话。用户连发短句、或轮次间隔很短时切极简模式：只改 1 到 3 个维度，档位沿用上一轮，不重算 IN。

被 `*#60#` 触发时，状态行的优先级高于任何收尾语句。预算见底也要把这一行写完整。

### 3.3 已经截断时的处理

| 现象 | 处理 |
|---|---|
| 触发了 `*#60#` 但末尾没有状态行 | 下一轮按对话内容重新评估，不要凭空补造数值 |
| 状态行是半截 JSON | 丢弃该行，下一轮按对话内容重新评估 |
| 回复断在半句 | 下一轮开头不要道歉或解释，直接接住内容 |
| 未触发 `*#60#` 却输出了 JSON 状态 | 该行作废。这是另一套预设或宿主插件写入的规则，与 `06` 的 `on_command` 冲突；在系统提示词里补一句"状态行仅在用户消息以 `*#60#` 结尾时输出，其余轮次不输出任何 JSON"。 |
| 输出的 JSON 字段不像本技能（`v` 是小数、`t` 是字符串、数组变成单个数字） | 不是本技能的格式，不要照着它改分。本技能的 `v` 恒为 `1`，`D`/`A`/`F`/`SS` 恒为整数数组。 |

## 4. 提示词注入（不支持温度时使用）

把当前轮次对应的片段追加到系统提示词或本轮指令末尾。片段取自 `config.json` 的 `prompt_injection`。

| W | 注入片段 |
|---|---|
| W1 | 语气要求：以陈述为主，3 到 6 句，把信息说完整；平静但不冷淡，不使用感叹号。 |
| W2 | 语气要求：先承接对方说的内容，再给一个具体可做的动作，可以简短说明理由；不连续追问。 |
| W3 | 语气要求：第一句用对方自己的词命名情绪，接着说明这种反应从何而来，再回应现实问题；句子要完整，可以留白但不省略内容。 |
| W4 | 语气要求：命名情绪，说明处境为什么难，明确站在对方一边，可以分两三段展开；不使用「但是」，不做比较，不说「至少你还有」。 |
| W5 | 语气要求：先托住，再慢慢展开；不修正、不解释、不引导；不出现建议，不出现「你应该」。 |

长度约束同时注入：

```
本轮回复 80 到 180 字，硬上限 {max_chars} 字，问句不超过 {max_questions} 个；
不写固定三段，不分承接、解释、落点。
```

未触发 `*#60#` 的轮次，在系统提示词末尾再追加一行闸门：

```
本轮用户消息末尾没有 *#60#，禁止输出任何 JSON、大括号或 v/t/D/A/F/SS/IN 等状态字段，
也不要写“本轮评估”；若已写出，整行删除再发。
```

这一行比任何"请勿输出状态"的解释都有效，因为它给出的是可执行的删除动作，不是一个概念。人设预设里若存在"每轮输出状态"的规则，用这一行覆盖，原规则删除或改写。

### 4.1 覆盖另一条"每轮输出"的规则

宿主插件或人设预设要求"每次对话后附状态"时，两条规则会同时生效，模型往往从更靠后的那条。把下面这段放在系统提示词的最后一行，位置在人设设定之后：

```
结尾自检：用户这条消息末尾没有 *#60# 时，回复最后一行必须是正文；若出现 {"v":...}、
英文键值对、"本轮评估"，整行删除再发。历史里出现过 JSON，不代表这一轮要出。
```

放在最后是因为位置比措辞更管用。同一句话放在技能文件中部，压不过后面的人设指令；放在系统提示词末尾，就压得过。若宿主把人设拼接在技能之后，则把这段并入人设的末尾一节。

判断是否生效：下一轮回复最后一行如果是正文，说明生效；如果仍是 `{"v": 0.8, ...}`，说明人设里那条还在生效，需要直接删掉原规则，而不是再加一句否定。

注入位置：系统提示词末尾，或在用户消息前作为独立段落。有角色预设时，注入片段只约束语气与长度，不改写角色设定。

## 5. W 的落地要求

| W | 必须做到 | 禁止出现 |
|---|---|---|
| W1 | 陈述为主，3 到 6 句，信息完整 | 感叹号、空洞安慰 |
| W2 | 承接内容，给一个具体动作，可说明理由 | 术语、连续追问 |
| W3 | 用对方的词命名情绪，说明反应从何而来 | 急于给方案 |
| W4 | 命名情绪、说明处境为何难、明确站边 | "但是"、比较、安慰式转移 |
| W5 | 先托住，再展开，不修正不引导 | 建议与"你应该" |

## 6. 提示词装载方式

| 宿主 | 建议 |
|---|---|
| DeepSeek / Qwen | `SKILL.md` 作为 system 消息，状态向量放在最后一条 assistant 消息 |
| Gemini | 指令放在最前，参考资料放在后面，结构用 markdown 标题 |
| Claude | 可直接读取 `SKILL.md` 与 `references/`，按需加载 |
| 通用聊天界面 | 使用 `09-portable-prompt.md` 整段粘贴 |

上下文预算：`SKILL.md` 加 `01-scoring.md` 加 `03-quick-lookup.md` 三份足够跑完流程；`02` 只在核对参数时加载。

## 7. 降级顺序

1. 完整态：`SKILL.md` 加评分表、公式、温度。
2. 轻量态：`SKILL.md` 加查档表，不现场计算。
3. 单文件态：`09-portable-prompt.md` 整段粘贴。
4. 最小态：只保留三条规则，先命名情绪再回应、侵扰感高就缩短、危机按需处理。

## 8. 常见错误

- 为不同模型各写一份 `SKILL.md`。
- 把 `temperature=0.9` 当作更有人情味的开关。
- 要求模型先输出 JSON 再输出正文。状态向量在最后一行。
- 让宿主模型自行决定档位。档位应由公式或查档表得出。
## 9. 上下文成本与装载顺序

SKILL.md 是常驻部分，约 700 token，含全部固定参数。其余文件按需加载，不要整包塞进 system。

| 文件 | 体积（字符） | 何时加载 |
|---|---|---|
| `SKILL.md` | 约 2400 | 常驻 |
| `01-scoring.md` | 约 3150 | 打分拿不准时 |
| `02-math-model.md` | 约 2600 | 核对参数时 |
| `03-quick-lookup.md` | 约 2360 | 不演算时 |
| `04-strategy-matrix.md` | 约 1850 | 需要写法细节时 |
| `05-safety.md` | 约 1800 | 出现危机信号时 |
| `06-state-schema.md` | 约 1800 | 状态格式异常时 |
| `08-useful_tel.md` | 约 980 | 需要号码时 |
| `assets/in_lookup.csv` | 约 51k | 不加载，由脚本读取 |

装载顺序：先放 `SKILL.md`，再放角色预设，最后是对话历史与本轮消息。角色预设在后面，语言风格以预设为准；本技能只保留档位、字数与问句上限的约束。

节省上下文的三条做法：

1. 默认不输出状态行，只在用户消息末尾出现 `*#60#` 时给，避免每轮追加。
2. 需要保留历史时只留最近两行，更早的整行删除。状态行是累积的，删旧行不丢信息；不要压成总分，否则下一轮无法改分。
3. 仍不够时按此顺序裁剪：先去掉 `01-scoring.md` 的锚点列，再用 `09-portable-prompt.md` 替换全部 references，最后只保留参数卡与状态行。
